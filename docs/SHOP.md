# Shop (products, cart, checkout, orders, payments) - CONTRACT

> Owner request: "create a new page to allow us to sell products such as jumpers, caps, T-shirts, stickers branded for the organisation as a way to raise
> funds to support our initiative. Create a panel in admin that allows us to configure the payment option, either mobile money, Visa, or even allow people
> to book for products. Make it clean and use some sample images to create the page." The owner chose **Flutterwave** as the online gateway.
> This file is the contract the shop was built on (foundation, storefront, admin, payments) and, with section 16, the record of what the integration pass found and fixed.
> EVERYTHING described here is built and tested: `php -d extension=gd bin/selftest-shop.php` (also run by `bin/selftest.php`) and the browser end-to-end runs listed in section 16.
> Read `docs/ARCHITECTURE.md` (conventions), `docs/DESIGN.md` (design system) and this file before writing code.

## 0. Honesty rules (read first)

* **No real payment gateway was contacted.** The Flutterwave integration is written against the documented v3 API and tested ONLY against the local mock
  `bin/dev/mock-flutterwave.php`. Real payments need the owner's merchant account and keys: **first try live payments in Flutterwave TEST mode with Flutterwave's
  test cards / numbers** (Admin > Shop > Payments says so). A green test here proves our code, not the real service.
* **Sample products are placeholders**: names, UGX prices, texts and pictures. The admin shows "Sample product - edit or delete"; the owner must replace them.
  The pictures are flat illustrations generated by `bin/dev/make-shop-samples.py`, not photographs. Prices are never presented as facts anywhere else.
* **No card data ever touches this server**: card and mobile-money payments happen on the Flutterwave hosted page (full-page redirect). We store only the gateway
  reference (`tx_ref`), the status and the amount.
* The shop **starts CLOSED** (`shop_open = 0`) and Flutterwave starts OFF: the owner reviews the samples, sets delivery and payments, then opens it.
* Delivery / returns / terms / privacy texts are neutral DRAFTS flagged for the owner (and a legal adviser) to review.

## 2. Data model (additive, idempotent)

Money columns are `DECIMAL(12,2)` in the shop currency; the code computes in integer MINOR UNITS (section 3). Every table has `id`, `created_at`, (`updated_at`).

* `shop_categories`: `slug(unique) name sort_order is_active`.
* `shop_products`: `slug(unique) category_id(FK set null) name summary(400) description(rich text) details(one line each) price sale_price sale_starts sale_ends sku track_stock stock_qty low_stock
  options(JSON) allow_booking is_featured is_sample status(draft|published|archived) sort_order seo_title seo_description`.
* `shop_product_images`: `product_id(FK cascade) path path_webp path_2x path_webp_2x width height alt sort_order is_cover`. Paths: `assets/img/shop/x.jpg` (bundled) or `shop/YYYY/MM/x.jpg` (under `uploads/`).
* `shop_orders`: `order_number(unique) token(unique, 40 hex) status payment_status payment_method customer_name customer_email customer_phone delivery_method delivery_address delivery_fee subtotal total currency
  customer_note staff_note payment_reference gateway_tx_ref gateway_attempts hold_until consent_at ip_hash paid_at stock_released`. **Personal data** from `customer_name` to `delivery_address`.
* `shop_order_items`: `order_id(FK cascade) product_id(FK set null) name options_text selection(JSON) unit_price qty line_total sku image` - a SNAPSHOT: later edits never change history.
* `shop_payments`: the ledger: `order_id method amount currency reference status(pending|success|failed|review|refunded|duplicate) source(customer|staff|gateway|webhook) gateway_id user_id meta`.
* `shop_order_log`: the timeline: `order_id kind message user_id`. No customer data.
* `shop_events`: the gateway log: `kind ref order_id status`. Never a payload, a name, an e-mail or a key.

JSON in `shop_products.options` (cleaned by `ProductService::normaliseOptions`, max 4 groups x 30 values):
`[{"key":"size","label":"Size","required":true,"values":[{"value":"m","label":"M","stock":null,"swatch":null}]}]`. `stock` per option value is optional (`null` = no limit of its own) and only
counts while the product tracks stock; the units available for one choice are `min(product stock, stock of each chosen value)`.

Indexes: orders by `(status, created_at)`, `(payment_status, created_at)`, `created_at`, `customer_email`, `hold_until`; products by `(status, is_featured, sort_order)`.

## 3. Money rules (`Money`)

* Everything is **integer minor units** (1 unit = 100). No floating point in any calculation; floats are only formatted to text first. `Money::parse('35,000') === 3500000`.
* Zero-decimal currencies (UGX, RWF, JPY ...) are shown and charged in whole units (`Money::roundTo` rounds half up); other currencies keep two decimals. `shop_currency` default `UGX`.
* Maximum amount `Money::MAX` = 9,999,999,999.99 (exactly what the `DECIMAL(12,2)` columns hold, so nothing accepted can fail in the database); overflow throws `OverflowException`, never wraps. An owner may set a unit price of at most `Money::MAX_PRICE` = 3,000,000.00: 30 lines x 99 units x that price plus a delivery fee still fits under `MAX`, so a cart or order total can never overflow. The product form rounds FIRST (0.4 UGX would be a free product) and then checks 0 < price <= MAX_PRICE. `Money::mul`, `Money::add`.
* Flutterwave gets `Money::gateway()` (int for UGX, 2-decimal float otherwise) and answers are read with `Money::fromGateway()` (never `(float)` comparisons).
* **`PricingService::quote()` is the ONLY place an order total is calculated**: subtotal = sum(price now x qty) of the lines; delivery fee = 0 for pickup, else the fee setting unless the subtotal reaches
  "free delivery for orders of at least" (0 = never free); total = subtotal + fee. The browser's prices are never used.

## 5. State machines

**Order status** (`OrderService::FLOW`; "->" = allowed next; `cancelled` and `refunded` are final):

```
pending    -> confirmed processing ready cancelled
confirmed  -> processing ready shipped completed refunded cancelled
processing -> confirmed ready shipped completed refunded cancelled
ready      -> processing shipped completed refunded cancelled          (ready = "ready for pickup")
shipped    -> completed ready refunded cancelled
completed  -> refunded
```
Rules: `completed` needs `payment_status = paid` (option `allow_unpaid` for a free / waived order); `refunded` needs a paid order and records the refund in the ledger; `cancelled` returns the reserved stock (always while unpaid;
while paid only if `shop_restock_on_cancel`); `refunded` returns it only if `shop_restock_on_refund` (default off: goods may come back damaged). Stock goes back **once** (`stock_released`). The customer is e-mailed after
`confirmed ready shipped completed cancelled refunded` (option `notify=false` skips).

**Payment status** (`PaymentService::FLOW`): `unpaid -> pending paid failed review`, `pending -> unpaid paid failed review`, `failed -> pending unpaid paid review`, `review -> paid failed unpaid refunded`, `paid -> refunded`.
`pending` = a gateway attempt is running OR the customer typed a transaction ID that staff must verify. `review` = something does not add up (amount / currency mismatch, money for a closed order): staff decide; review orders never expire.
Money held by a CANCELLED order (paid before the cancel, part paid, or a payment that arrived after it and sits in `review`) is closed by staff with `PaymentService::staffSetStatus(id, 'refunded')` (the "Record the refund" button on the order page): it writes one `refunded` ledger row for `refundableMinor()` and sets payment_status `refunded`. It is allowed only for a `cancelled` order that has money (error `nothing_to_refund` otherwise). A live order is still refunded through `OrderService::setStatus('refunded')`. Ledger statuses: `pending success failed review refunded duplicate superseded` (`superseded` = a reference the customer typed that was never matched because staff recorded the money under another one).

**Holds** (stock is reserved when the order is created, inside the transaction, with row locks): an unpaid order keeps its stock until `hold_until` (book and pay-on-pickup: `shop_hold_days`; mobile money / bank:
`shop_manual_hold_days`; online: `shop_gateway_hold_hours`; a customer's transaction ID extends the manual hold). `OrderService::releaseExpiredHolds()` cancels orders still pending + unpaid / waiting / failed past
that time - but an order with an online try that may still turn into money is first CHECKED WITH THE GATEWAY (`OnlinePayment::recheck`, at most 2 orders per lazy call at checkout, 10 per cron run), so a payment whose webhook was lost is recorded instead of cancelled. It runs lazily at the start of every `create()` and from `bin/shop-maintenance.php`. Any status change away from `pending` (including staff confirming a booking or an order) clears `hold_until`.

**Booking** is not a separate product: a product with `allow_booking = 1` can be reserved; `PaymentMethods::available(true)` (every cart item allows booking) offers the method `book`; "Book / reserve this item" posts `mode=book` and
sets the cart preference, so checkout preselects it.

## 6. Flutterwave flow (exact fields)

Base `https://api.flutterwave.com` (fixed host, https only, TLS verified, no redirects, 8 s / 20 s timeouts, 1 MB cap); header `Authorization: Bearer <secret key>`.

1. **Start** (`OnlinePayment::begin`, from checkout or the "Pay now" button, a POST): `PaymentService::startAttempt` -> new `tx_ref = <order number>-<attempt>` (attempt 1..10), ledger row `pending/gateway`, order payment `pending`, hold extended.
   `POST /v3/payments` body: `tx_ref, amount, currency, redirect_url (= /shop/pay/return/{rid}, see step 2), payment_options ("card,mobilemoneyuganda", admin-configurable), meta{order_number}, customer{email, phonenumber, name},
   customizations{title, description, logo}`. Response `{"status":"success","data":{"link":"https://checkout.flutterwave.com/v3/hosted/pay/..."}}`. The link is accepted only if https on `flutterwave.com`
   (or, in dev mode, the mock origin); the customer is redirected to it.
2. **Return** (`GET /shop/pay/return/{rid}?status=&tx_ref=&transaction_id=`): the order number is NOT a credential (it is printed on receipts and e-mails, quoted as the payment reference and shown in the gateway dashboard), so a return is acted on only when `{rid}` = `OnlinePayment::returnKey(tx_ref)` = the first 32 hex characters of HMAC-SHA256(`APP_KEY`, `shop-return|` + tx_ref). We put that key in the `redirect_url` path (a path segment, so the gateway can append its own query string); only our server can compute it. Without a valid key (old link, guessed number, bot) the answer is ONE neutral "Thank you" page (200, `no-store`, no cookie, no lookup, no gateway call, nothing about any order) - identical for a real and an invented reference. With the key: **nothing else in the query is trusted**. Only `tx_ref` is read (format-checked) and must belong to an order (`PaymentService::orderForTxRef`: order number + attempt
   started + ledger row). Then `GET /v3/transactions/verify_by_reference?tx_ref=...` -> `{"status":"success","data":{id, tx_ref, flw_ref, amount, currency, status, ...}}`; then 302 to the order page (`private, no-store`).
3. **Webhook** (`POST /shop/webhook/flutterwave`): header `verif-hash` compared (constant time) with the admin-configured secret hash: missing / wrong / no hash configured -> **401**, nothing processed. Authentic -> only `data.tx_ref` is taken from
   the body (amounts and status in the body are ignored), then the same verify call; the answer is always **200** (even unknown references, garbage bodies and our own errors) so Flutterwave does not hammer us. Idempotent: a
   replay does nothing.
4. **Settlement** (`PaymentService::settleGateway`): the order is marked **paid only if** the verified transaction is `successful` (only that word; `completed` is not accepted) AND its `tx_ref` equals the asked one and belongs to this order AND `amount >= order total` AND
   `currency` equals the order currency. Any other "successful" answer sets the order to **review** (no payment). `failed` -> payment `failed` (the order stays open: "Pay again" starts attempt n+1 with a new tx_ref) - unless it is an EARLIER try than the order's latest `tx_ref`: then only that try's ledger row is closed (state `superseded`) and the order's payment status is left alone;
   `pending` -> unchanged; a cancelled click on the hosted page only changes the wording.
5. **Paid** -> ledger `success`, `paid_at`, hold cleared, order auto-confirmed (`shop_auto_confirm_paid`), receipt e-mail to the customer + notice to staff.
6. Staff can "re-check with the gateway" (`OnlinePayment::recheck`); it verifies EVERY open try of the order (all pending gateway ledger rows, `PaymentService::openGatewayRefs`), not only the latest, and works on a cancelled order too (money that turns up for a closed order becomes `review`, never hidden). `bin/shop-maintenance.php` runs the same re-check FIRST for waiting attempts older than 5 minutes - including orders cancelled in the last 7 days - and only then releases expired holds. "Pay now / Pay again" asks the gateway about the open tries before it opens another payable link (`already_paid` / `under_review` instead of a second charge).
7. Test connection: `GET /v3/transactions/verify_by_reference?tx_ref=lumina-connection-test` (authenticated, no side effect): a normal JSON answer ("no transaction found") = key accepted; 401 = key rejected. Documented assumption: Flutterwave
   answers an unknown reference with a JSON error, not 401 - to be confirmed in TEST mode.
8. Dev override: `.env FLW_DEV_BASE_URL=http://127.0.0.1:PORT` is read **only when `APP_ENV=local`** and only for `127.0.0.1` / `localhost` / `[::1]` without path or credentials; otherwise ignored, so production can never be pointed elsewhere.

Setup checklist for the owner (shown in the admin panel): create a Flutterwave account and finish verification; copy the TEST public key, secret key and (Settings > Webhooks) set the webhook URL (`https://<site>/shop/webhook/flutterwave`)
and a secret hash; paste them in Admin > Shop > Payments; press "Test connection"; place a test order with Flutterwave's test card / mobile-money test numbers; only then switch the mode to live and replace the keys with the live ones.

## 7. Secrets (`SecretStore`)

* Stored in `settings` as `shop_secret_<name>` = `enc:v1:` + base64url(iv 12 | tag 16 | ciphertext): **AES-256-GCM** (openssl), key = HKDF-SHA256 of `APP_KEY` (`Config::appKey()`), info `lumina-shop-secrets-v1`.
  Tampered / truncated values and a changed `APP_KEY` read as `null` (the admin sees "stored but cannot be read, enter it again"); `APP_KEY` must therefore be set in the production `.env` and never changed.
* `.env` alternative wins: `FLW_SECRET_KEY`, `FLW_SECRET_HASH` (and the non-secret `FLW_PUBLIC_KEY`, `FLW_MODE=test|live`); the panel shows "Set in the .env file".
* A secret is **never shown again** after saving (only "set" / "replace" / "clear"), never in logs, audit details, JSON responses, e-mails or the event log. The generic Site settings screen cannot see these keys (they are not in `settings_schema.php`).
* The public key and the mode are not secrets and are stored as plain settings.

## 16. Integration pass: what was found, fixed and verified (read before changing the shop)

**Defects found by running the real thing in a browser (all fixed, each guarded by a check):**

1. **CSP `form-action 'self'` blocked the payment redirect.** Both ways to start an online payment (the checkout form and the "Pay now" button) are form POSTs; Chrome and Edge apply `form-action` to the redirect that follows a form post, so the 302 to `checkout.flutterwave.com` was blocked ("Sending form data ... violates the following Content Security Policy directive"). Firefox and Safari would not have shown it. The policy was NOT loosened: the POST now answers 200 with a small page (`web/shop/redirecting.php`, trait `GatewayRedirects`) carrying `<meta http-equiv="refresh">` and a visible "Continue to payment" button. A meta refresh is a normal navigation, works without JavaScript, and needs no CSP change. The link is still only ever `https://*.flutterwave.com` (or the local mock while `APP_ENV=local`).
2. **`{iid}` (picture id) reached the controller as a string** (the router only casts a parameter called `{id}`): `ShopImagesController::update/destroy` threw a TypeError, so "Main picture" and "Delete picture" answered HTTP 500. Fixed, and `bin/selftest-shop.php` now fails if any shop route has a strict-`int` parameter the router does not cast.
3. **A form field called `method` breaks `assets/js/admin.js`** (`form.method` becomes the field, `.toLowerCase` is not a function). The order screens use `via` / `paid_by` instead.
4. **A mobile-money / bank transaction ID could pay two orders.** `PaymentService::markPaid` (staff) now refuses a reference that already paid ANOTHER order (`reference_used`, message in the admin); the owner adds a letter if one transfer really paid for two.
5. `bin/selftest-forms.php` had lost its CR/LF characters inside a regular expression (an editor mangled them) and failed three e-mail checks: restored from git with only the intended string change.
6. The cart page replaced itself with the JSON answer when the background request carried `X-Requested-With`; the background cart requests now follow the redirect and swap in the fresh HTML.
7. No-JavaScript gaps: the delivery address box and the stock fields were hidden by the server; now only the scripts hide them.

**Added by the integrator:** the real storefront and admin screens (the architect had left plain reference views and stubs), `/shop/terms`, header cart link (hidden until something is in the cart; reads the session only if it already exists, so anonymous pages stay cookie-free), dashboard tile "Shop orders to handle", sitemap entries for published NON-sample products and their categories, schema.org `Product` data and `noindex` rules (a SAMPLE product has no structured data, is `noindex` and is not in the sitemap: its price is a placeholder), icons `printer key credit-card truck`, README cron line and go-live checklist, `docs/CONTENT_NOTES.md` section 15.
