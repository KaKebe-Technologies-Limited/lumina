# Lumina Africa Foundation - website + admin CMS

Organisation website for **Lumina Africa Foundation** (Gulu City, Northern Uganda) with a full admin CMS.
PHP 8.2 - MySQL/MariaDB - SCSS - vanilla JS. No Composer, no Node.

* **Every public page is editable from the admin** (headings, paragraphs, buttons, pictures and alt text, section on/off, SEO text,
  menu entry), and the owner can create new pages. Nothing is hard-coded: with an empty database the site still renders the
  built-in wording; the admin only stores what the owner changes.
* **All organisation pages are part of the site and the menus**: About, Our Team, Partners, Reports & Downloads, Programs, Projects,
  Involvement, **Membership** (online registration for people and organisations who want to join), Careers, Activities, Events, Gallery, Blog, News (and `/press`), Impact Stories, Contact (with the **Calendar** underneath), Donate, Privacy.
  Pages whose content is not added yet show a friendly empty state instead of disappearing. The owner can hide any page from the
  menus under **Admin > Menus**, or unpublish it under **Admin > Pages**.

**The web root is the project root** (there is no `public/` folder): `index.php` is the front controller; static files live in
`assets/` (css, js, img) and uploaded images in `uploads/`. Everything else (`app/ bin/ database/ docs/ scss/ storage/ tools/ vendor/`,
`.env`, `*.sql`, `*.md`, ...) is blocked from the web by the root `.htaccess` and by a deny-all `.htaccess` inside each folder.
The base URL is computed at runtime, so the same files work at `http://localhost/lumina/`, at a domain root or in any sub-folder.

## Run locally (XAMPP on Windows)

1. Start Apache and MySQL in the XAMPP control panel. Put the project in `C:\xampp\htdocs\lumina`; the site is then at <http://localhost/lumina/>.
2. `copy .env.example .env` (the defaults suit XAMPP: user `root`, empty password, database `lumina`).
3. Create the database, tables, starter content and a development admin account:
   `C:\xampp\php\php.exe bin\setup.php` (add `--fresh` to drop and recreate the local database; `--no-seed` to skip `database/seed.sql`).
   The script is safe to run again: it never deletes content, and it adds a `pages` row for every page file in `app/config/pages/`.
4. Compile the stylesheets (libsass through Python's `sass` module; `assets/css/*.css` are generated, never edit them by hand):
   `python bin\build-scss.py` (use the Python that has the `sass` module; `--watch` rebuilds while you edit `scss/`).
5. Open the site <http://localhost/lumina/> and the admin <http://localhost/lumina/admin>.
   The development admin e-mail and password are in `storage/dev-admin-credentials.txt` (git-ignored; delete the file when done).
   More accounts: `php bin/create-admin.php --email=owner@example.org --name="Site Owner" --role=admin` (roles: `admin`, `editor`).

Local development accepts only dev-looking host names (localhost, 127.x, private-network addresses, single-label names, `*.test` / `*.local` / `*.localhost`)
while `APP_URL` is empty; anything else gets HTTP 400.

Other ways to run it: `php -S 127.0.0.1:8099 index.php` from the project root (built-in server; serves only `assets/` and `uploads/` as
static files, everything else goes through the app). Health check: `php bin/selftest.php` must print `ALL CHECKS PASSED` (it includes the partners, newsletter, live-reflection and membership-card suites (engines, flows, HTTP, staff, designer and review regressions); run it once with `-d extension=gd` and once without).

## Using the admin

Sign in at `/admin`. The sidebar has everything:

| Group | Screens |
|---|---|
| Site | Dashboard, **Pages** (edit the wording, pictures, buttons, SEO and menu entry of every page; create new pages), Menus, Impact figures, FAQs |
| Content | Programs, Projects, Posts (blog, news, press), Activities, Gallery, Jobs |
| Organisation | Team, Partners, Documents (reports), Events (with registrations), Impact stories |
| Inbox | Messages, Subscribers, Involvement requests, Job applications, Donations |
| Membership | **Members** (applications, approval, membership numbers, headshot and proof-of-payment checks, payments and printable receipts, renewals, membership cards, CSV export), **Needs proof check** (badge), **Membership card** (the card designer, ability `members.card`, admin only unless given to a custom role), **Membership types & fees** (admin role only: this is where each fee and the type code of the member number are set) |
| Calendar | **Calendar & schedule** (month view, click a day to add a date, list and search, bulk show/hide), **Holidays & days** (confirm the Eid dates, change one year), **Types & colours**, Import / export (CSV), Settings (admin role only) |
| Administration (admin role only) | Site settings, Users, Activity log |

* **Edit a page's text**: Admin > Pages > *Edit*. Each section is a card; change a field and Save. "Reset to default" restores the built-in wording.
  Sections with a switch can be hidden. Repeating lists (values, FAQ, steps...) can be added to, reordered and trimmed. The Pages list also has
  a shortcut to the screen that holds each page's items (for example Team page -> Manage team members).
* **Add the people and files an organisation page shows**: Team, Partners, Documents, Events and Impact stories each have their own screen.
  Impact stories are published only after you tick that the person's consent is confirmed.
* **Partners (About page)**: Admin > Partners is a card screen. Type the name, drop the logo in the box, press **Add** and the logo is on the website at once: the "Our partners" section of the About page, the Partners page and the footer strip all read the same list. Each card has a show/hide switch, inline edit, replace/remove logo, delete (with a confirmation that also offers "Hide instead"), bulk actions and drag-and-drop or arrow-button ordering. Logos are trimmed, resized, given a 2x and a WebP copy and shown in identical boxes; a flat light off-white background (for example a JPEG on #F4F4F0) is made transparent. The footer strip shows the first 12 partners (Admin > Pages > Site-wide content > Footer) with a "See all partners" link; About shows its own number (default 24); the Partners page shows everyone. Upload a PNG with a transparent background (at least 400 px wide); a white-on-transparent logo vanishes on the light boxes. The image library (PHP `gd`) is needed for the trimming and resizing: without it the logo is stored as uploaded (metadata removed) and the admin says so. After a code upgrade press **Optimise existing logos** once if GD is on. Nothing is cached: a change is visible on the next page load. Details: `docs/PARTNERS_NEWSLETTER.md`.
* **Newsletter (two formats)**: Admin > Newsletter > **Write an issue** (online editor) or **Upload a PDF issue** (PDF up to the limit shown on the screen, 25 MB by default, never above the server's own upload limit). PDFs are kept outside the web root and streamed by the site, so unpublishing or deleting an issue takes the file offline immediately; visitors get a viewer (from tablet width up), **Download PDF** and **Read in a new tab**. An online issue can also carry a PDF download. PDFs are checked over their whole length (scripts, launch actions and hex-escaped names are refused at any size) and the PDF download routes are rate-limited. Every issue has a **Live on the website** box that says whether visitors can see it and, if not, why (draft, scheduled, archived, page switched off), with a "Check the website now" button. The newsletter is in the header menu under **Blog > Newsletter**, in the footer, on the Home page (latest issue card) and on the Blog page. Details: `docs/NEWSLETTER.md`, `docs/PARTNERS_NEWSLETTER.md`.
* **Membership**: people apply at `/membership/register`. Staff review them under Admin > Members (approve, reject with a reason, record a payment, print a receipt, renew). The **fee of each membership type is set in Admin > Membership types & fees** and only affects new applications (each member keeps the fee agreed when they applied). Until a fee is set the website says "Fee to be announced". The page can be switched off with **Site settings > Membership > Accept applications**. Registration ships **closed**: switch it on after setting the fees, replacing the placeholder terms and reviewing the privacy section. Details: `docs/MEMBERSHIP.md`.
* **Membership card** (headshot, proof of payment, automatic card): the registration form asks for a **headshot** (required by default, with a consent tick) and optionally a **proof of payment**; applicants can add or replace both later on their **private page** `/membership/me/<private link>` (no password: the link, sent in their e-mails, is the credential; it also shows their progress and the card). Staff check the proof under Admin > Members (verify it, or ask for a better copy, which sends a polite e-mail), and can replace, frame or remove the photo. When a member is **approved and the balance is paid or waived**, a **membership card** (PDF, same layout as the owner's reference `docs/design-reference/membership-card-reference.pdf`: member number such as `LAF-IND-26-0001`, photo or initials, QR code, valid-until date) is generated automatically and e-mailed as a PDF attachment; a renewal issues a new version. The QR code opens `/membership/verify/<token>`, which shows only VALID / EXPIRED / SUSPENDED / NOT VALID, the name, type, number, member-since and valid-until (never a photo, e-mail or phone). **Admin > Membership card** changes the logo, colours, wording, blocks, number format, **when cards are issued** (when paid and approved, as soon as approved, or manual) and the card e-mail, with a live preview; the code in the number (IND, YTH, ORG) is set per type under Membership types & fees. Photos and proofs are private files (`storage/private/members`, never served by the web server), deleted when a member is erased and 90 days after a rejection or cancellation (a setting; run `bin/membership-maintenance.php` daily by cron). **On the live host:** import `database/lumina-live-import.sql` first, set `APP_URL` in `.env` (the QR code and e-mail links use it) and make sure PHP's GD extension is on (without it the card PDF still works, but photos are not cropped or rotated and there is no picture preview). Have the retention period, the photo-consent wording and the privacy text reviewed by counsel (Uganda Data Protection and Privacy Act, 2019). Details: `docs/MEMBERSHIP_CARD.md`.
* **Calendar and schedule**: the public page is `/calendar` (also shown on the Contact page, with an "Add to my calendar" file for every date). It ships with the Uganda public holidays and the main international and UN days; **Eid al-Fitr, Eid al-Adha and Safer Internet Day show "Date to be confirmed" until you confirm the day** (the Eid days already announced for 2024-2026 come pre-confirmed with their source; a predicted Eid day is usually the day shown or one day earlier; Admin > Calendar > Holidays & days; the sidebar badge and the dashboard card count dates to confirm). Add your own programme sessions, meetings and deadlines with **Add a date** (or click a day; repeating dates and a CSV import are supported; a repeating date cannot last as long as the gap between repeats). Unpublishing the Calendar page also closes its JSON feed and the .ics downloads. No programme session is pre-filled: the owner adds them. Details: `docs/CALENDAR.md`.
* **Meeting scheduler** (Admin > Calendar & schedule > Meetings, or the button **Schedule a meeting** on the Calendar manager and in the Inbox): create a meeting with its date and time (East Africa Time), a link and an agenda, invite people by typing or pasting e-mail addresses, searching your members, choosing staff or picking people from earlier meetings, then press **Save and send invitations**. Each person gets their own e-mail with a calendar file and **Accept / Maybe / Decline buttons that open their personal meeting page** `/meeting/<private link>` (answers are recorded there; a reply made inside Gmail or Outlook itself goes to the organiser's mailbox and is not recorded on the site), and later updates, a cancellation or reminders. **The site cannot create Zoom, Google Meet or Teams rooms:** paste the link you made there. The one built-in option is "Generate a free private video room", a link on the free external service Jitsi Meet (meet.jit.si, run by someone else); nothing is created until somebody opens the link. Meetings are **private by default**; a public meeting shows only "Meeting", the title, date and time on the public calendar (the join link only if you tick that box, which lets strangers join). Visitors can ask for a meeting from the Contact page; requests arrive in Admin > Calendar & schedule > Meeting requests, where "Schedule this meeting" pre-fills the form. No sample meeting is pre-filled. **Invitations need working SMTP** (see the mail notes below): with `MAIL_DRIVER=mail` many mailboxes (Gmail, Outlook) reject or hide calendar invitations, so set `MAIL_DRIVER=smtp` and send yourself a test invitation first ("Send me a test invitation" on the meeting page). Wording of the invitee page and of every e-mail: Admin > Pages > Meetings; request topics and defaults: Site settings > Meetings. Details: `docs/MEETINGS.md`.
* Editors can edit content and handle the inbox; only admins manage settings, menus structure, users, deletions of inbox data and the activity log.

## Deploy to production (Linux / shared hosting)

0. The host needs **PHP 8.1+ (8.2 recommended)** with the extensions `pdo_mysql`, `mbstring`, `dom`, `fileinfo`, `ctype`, `json` (the front
   controller stops with a readable message when one is missing) and, recommended, `gd` (resizes photos; without it photos are still cleaned of GPS/camera
   data by a built-in cleaner) and `exif`. Admin > Site settings > System check shows what is missing.
1. Upload the project so that the **document root is the project folder** (the folder that contains `index.php`). Do not upload `.git`,
   `storage/*` or a development `.env`.
2. Copy `.env.example` to `.env` and set at least:
   `APP_ENV=production`, **`APP_DEBUG=0`**, **`APP_URL=https://your-domain`** (no trailing slash; REQUIRED outside `local`, the site answers 500 without it:
   links in e-mails, canonical addresses and the sitemap are built from it, never from the Host header; other Host names get HTTP 400 unless listed in
   `ALLOWED_HOSTS`), database `DB_*`, `MAIL_DRIVER=mail`, `MAIL_FROM`, and a long random `APP_KEY` (or leave it empty and keep the generated
   `storage/app.key`; if `storage/` is not writable set `APP_KEY`). **Behind a reverse proxy / CDN / load balancer set `TRUSTED_PROXIES`** (IPs or CIDR ranges):
   without it every visitor looks like one IP and shares the form and login rate limits.
   Keep `.env` out of version control and make sure it is not readable by the web (the root `.htaccess` already denies it).
3. **With a shell**: run `php bin/setup.php` once (creates tables, starter content and page rows), then create the real admin with
   `php bin/create-admin.php --email=... --name=... --role=admin` (without `--password` a random one is generated into
   `storage/dev-admin-credentials.txt` and the account must choose its own password at first sign-in), then **delete
   `storage/dev-admin-credentials.txt`**. `setup.php` also creates a throw-away admin when no user exists: remove or disable it
   once your own account works (Admin > Users).
   **Without a shell (shared hosting / phpMyAdmin)**: create the (empty, utf8mb4) database in the hosting panel, select it in phpMyAdmin and *Import*
   `database/schema.sql`, then `database/seed.sql` (starter content; optional). Put a long random `INSTALL_TOKEN` (16+ characters) in `.env`, open
   `https://your-domain/install`, enter the token and the details of the first administrator, then **remove `INSTALL_TOKEN` from `.env`**. The page answers 404
   unless the token is set and no user exists yet.
4. `storage/` and `uploads/` must be writable by the web server user. Compiled CSS is committed in `assets/css/`; recompile with
   `python bin/build-scss.py` only if you change `scss/`. `storage/sessions` is cleaned by PHP itself; visitors without a session cookie never create a session file.
5. Serve the site over **HTTPS** (the app sends HSTS and secure cookies on HTTPS). Apache needs `mod_rewrite` and `AllowOverride All`
   so that the `.htaccess` files are honoured. On Nginx/other servers, replicate them: deny `app/ bin/ database/ docs/ scss/ storage/ tools/ vendor/`,
   dotfiles, `*.env *.sql *.md *.py *.log`, and send every request that is not an existing file under `assets/` or `uploads/` to `index.php`.
6. After deploying, check that these return 403/404 and never file contents: `/.env`, `/app/config/app.php`, `/storage/app.key`,
   `/database/schema.sql`, `/bin/setup.php`, `/docs/ARCHITECTURE.md`, `/public/`, `/backup.zip` (any file that is not under `assets/` or `uploads/`),
   `/install` (404 once an admin exists). Run `php bin/selftest.php` locally before a release (it refuses to run outside `APP_ENV=local`).
   **Upgrading a live database**: re-importing `database/lumina-live-import.sql` (rebuilt with `php bin/build-import-sql.php`) is safe, and **must be done first (or together with the code upload)**: new code against the old schema answers 500 on `/membership`, Admin > Members and `/newsletter` (the footer link to the newsletter hides itself while its table is missing). It only adds missing tables (`membership_types`, `members`, `member_payments`, `newsletters`, `newsletter_revisions`, `newsletter_deliveries`, and the eight `shop_*` tables: with the shop closed, the six sample products inserted once, the five Shop abilities added to the built-in Editor role only while its list is still the factory list, and the Shop page under Donate in the menu once), the three guarded columns of `members` plus the guarded photo, proof, private-link and card columns of `members`, the proof columns of `member_payments` and the `code` column of `membership_types` (existing members, payments, numbers and roles are untouched; the private-page link of an old member is created the first time it is needed), the 50 card settings (never overwriting a value the owner changed), the `members.card` ability, the type codes IND / YTH / ORG (only for types that have none), settings and page rows, never overwrites anything the owner edited, and re-creates the three placeholder membership types only while that table is empty, and adds the one sample **draft** newsletter issue only while the `newsletters` table is empty (it is not public until the owner publishes it; edit or delete it under Admin > Newsletter). The calendar needs the tables `calendar_types`, `calendar_entries` and `calendar_overrides` (added by the same import, together with the 14 Uganda public holidays and the international days, only while they are missing or unedited; a holiday you renamed, hid or changed is never overwritten). Until the import is done `/calendar` answers 404 and the Contact page simply omits the calendar block.
   **Upgrade steps (live site)**: (1) back up the database; (2) import `database/lumina-live-import.sql` in phpMyAdmin (repeating it is harmless); (3) upload the new code; (4) only if you want to e-mail issues: add the SMTP lines to the server `.env` (next paragraph), set the sender under Site settings > Newsletter, send a test from the issue's E-mail page; (5) check `/newsletter` (friendly empty page until the first issue is published) and Admin > Newsletter. **Partners / PDF newsletter upgrade**: the same import adds the logo columns of `partners` and the PDF columns of `newsletters` (all additive, existing rows untouched; a published issue stays published, existing logos keep working and are marked "not optimised") and moves the Newsletter page into the header menu under Blog once (if you later hide it in Admin > Menus it stays hidden). Import first, then upload the code, then Admin > Partners > Optimise existing logos. The server needs the PHP `gd` extension for logo trimming (ask the host to keep it on); PDFs need no extension. After uploading code, if the host's OPcache is set not to re-check files, ask it to reset OPcache.
   **Newsletter e-mail (optional, needs SMTP)**: the newsletter can be e-mailed to the subscribers (Admin > Newsletter > an issue > E-mail). For that set
   `MAIL_DRIVER=smtp` and the SMTP login of your mailbox in `.env` (Hostinger: hPanel > Emails > the mailbox > Configuration):
   `MAIL_HOST` (e.g. `smtp.hostinger.com`), `MAIL_PORT` (`465` with `MAIL_ENCRYPTION=ssl`, or `587` with `MAIL_ENCRYPTION=tls`), `MAIL_USERNAME`, `MAIL_PASSWORD`,
   `MAIL_FROM` (an address that mailbox may send from), optional `MAIL_TIMEOUT` (seconds, default 20) and `MAIL_CAFILE` (a CA bundle, only if the server has none).
   Put the password in double quotes if it contains a `#`. The login lives ONLY in `.env`: never in the database, the admin or the logs. Certificates are always
   verified and a login is never sent without encryption. Sender name, reply-to, footer text, batch size and subject prefix are under **Admin > Site settings > Newsletter**.
   A wrong SMTP login, a TLS problem or a message above the server's size limit pauses a sending at the very first message (nothing is marked failed or "sent"): fix the `.env`, then press Resume. While a sending runs or is paused the issue cannot be edited (cancel the sending first), so every subscriber receives the same message. Deleting a subscriber also removes the address from the sending records of every issue.
   Keep `MAIL_DRIVER=mail` (or `file` locally) if you do not e-mail issues: the web page of the newsletter does not need SMTP. Optional cron job (hPanel > Advanced > Cron jobs)
   that finishes interrupted sendings: `php /path/to/lumina/bin/newsletter-send.php` every 5 minutes (see `docs/NEWSLETTER.md`). It needs `APP_URL` in `.env` (links in the mails are built from it), only runs from the command line, and prints nothing unless you add `--verbose`. Without the cron job a sending simply continues the next time someone opens the issue's E-mail page and presses "Continue sending".
   **Meeting scheduler e-mail (Admin > Calendar > Meetings, needs SMTP too)**: invitations, updates, cancellations and reminders use the same `.env` mail login and the sender set under Site settings > Newsletter (each person gets their own e-mail; the organiser's address is only the Reply-To, never the From address). Second optional cron job, **it also sends the 24-hour and 1-hour reminders**, so add it if you switch reminders on:
   `0-59/5 * * * *  /usr/bin/php /home/ACCOUNT/domains/DOMAIN/public_html/bin/meetings-send.php` (every 5 minutes, same `APP_URL` rule, prints nothing unless `--verbose`, see `docs/MEETINGS.md`). It finishes queued sendings and sends only reminders that are due and not yet sent; it shares one database lock with the "Send" buttons, so nobody is e-mailed twice. Without it, invitations still go out from the meeting page, and reminders only when somebody presses "Send reminder now". A wrong mail login pauses a meeting's sending at the first message (nobody is marked failed): fix `.env`, then press Resume on the meeting page.
   **Forms (Admin > Forms: job applications, registrations, surveys, any form you design; needs SMTP only for the e-mails)**: staff notifications and confirmations use the same `.env` mail login and the notification list under Site settings > Forms (or the site notification e-mail). The mail to staff only carries a link to the answers, never the answers themselves, unless you tick that on the form. Fourth optional cron job (daily): `17 3 * * *  /usr/bin/php /home/ACCOUNT/domains/DOMAIN/public_html/bin/forms-maintenance.php --quiet` - it deletes answers (and their private files) that are older than the retention period you set on each form, and removes stray upload files; add `--dry-run` to only print the counts. Without the cron job the same clean-up runs by itself (at most every 6 hours) whenever someone opens the Forms or answers screens. Uploaded files live in `storage/private/forms` (never reachable by a URL) and are limited by the host's `upload_max_filesize` / `post_max_size` (the form builder shows the effective maximum). Forms collect personal data: set a retention period (only people who may delete forms can set or shorten it, because the answers are deleted for good), check the consent wording and decide who gets the "Form answers" ability (Admin > Roles; it is also what allows e-mailing the answers themselves). Uploaded PDFs and Office files are checked for scripts, macros, embedded files and remote links - open applicants' files in a protected viewer anyway - see `docs/FORMS.md` and `docs/CONTENT_NOTES.md` section 14.
   **Shop (Admin > Shop: products, orders, payments; needs SMTP only for the order e-mails)**: the shop ships CLOSED, with six SAMPLE products (placeholder names, prices and pictures). Fifth cron job, **every 15 to 30 minutes**: `*/20 * * * *  /usr/bin/php /home/ACCOUNT/domains/DOMAIN/public_html/bin/shop-maintenance.php > /dev/null 2>&1` - it first re-checks online payments that are still waiting after 5 minutes - every open try of the order, and orders cancelled in the last 7 days too (it catches a lost Flutterwave message; money found for a cancelled order is flagged for you to refund) - and then cancels unpaid orders whose stock hold has run out (the items go back on sale). Only runs from the command line and prints one summary line (counts only, no customer data): keep the `> /dev/null 2>&1` at the end of the cron command so your host does not e-mail you that line every 20 minutes (real failures are still written to the application log). Without this cron job, holds still expire whenever somebody places an order, but stale orders and missed payment messages are only cleaned up when someone opens them. **Go-live checklist** (full detail in `docs/SHOP.md`):
   1. Set `APP_URL=https://your-domain` and keep `APP_KEY` in the production `.env` and never change it (it encrypts the gateway keys saved in Admin > Shop > Payments; a changed key makes them unreadable).
   2. Admin > Shop > Products: replace or delete every sample product (names, UGX prices, photos). Admin > Shop > Shop settings: collection address and hours, delivery fee and areas, the e-mail addresses that get new-order e-mails, and READ the draft terms, delivery, returns and privacy wording (have a legal adviser check it).
   3. Admin > Shop > Payments: switch on the ways to pay you really offer and fill in the mobile-money numbers and bank details. For **Flutterwave** (card and mobile money online): create the account, paste the **TEST** public key, secret key and a long random webhook hash, set the webhook address shown on that screen in Flutterwave (Settings > Webhooks, same hash), press **Test connection**, and place a **test order with Flutterwave's test card / test mobile-money numbers** until the order turns Paid. The integration was written from Flutterwave's v3 documentation and only ever run against a local practice server, **never against the real service**: do not skip this step. Only then switch the mode to LIVE and replace the keys and the webhook with the live ones (the screen warns when the key kind and the mode differ). Card numbers never reach this site: the customer pays on Flutterwave's page.
   4. A cancelled order that still holds money (paid before the cancel, or a late payment) shows **Record the refund** on its page: return the money from Flutterwave, mobile money or the bank first, then record it there. Mobile-money and bank orders are NOT confirmed automatically: someone must check the statement and press "Mark as paid" on the order (the screen lists what to check).
   5. Admin > Shop > Shop settings > "The shop takes orders" - open the shop last. Give the Shop abilities (Admin > Roles) only to people who may see buyers' names, phones and addresses; the gateway keys need "Shop, delivery and payment settings" (administrators by default).
   **Social media (Admin > Social media: profile links, automatic posting of published newsletters, the Share kit)**: the **profile links** (Facebook, Instagram, X, LinkedIn, TikTok, YouTube, WhatsApp, Telegram, Threads) are shown in the footer, on the Contact page, in newsletter e-mails and on the maintenance page as you choose. **Auto-share channels** post a newsletter issue the moment it is published (or when its scheduled time comes): Facebook Page, Instagram (Business / Creator account linked to a Page; the picture is hosted at an unguessable address; no clickable links in captions), X, LinkedIn (organisation Page), a Telegram channel and a **webhook** for Zapier / Make / IFTTT / Buffer, which is also how you reach **TikTok** (TikTok's own posting API cannot carry a text and link newsletter, so there is no direct TikTok channel; the **Share kit** gives you ready captions and the images to post by hand in a minute). **Every platform needs YOUR OWN developer app or bot**: the steps are shown on each channel card. Keys and tokens are stored **encrypted** (like the shop keys: keep `APP_KEY` in the production `.env` and never change it) or can be put in `.env` (`SOCIAL_FB_PAGE_TOKEN`, `SOCIAL_IG_TOKEN`, `SOCIAL_X_API_KEY`, `SOCIAL_X_API_SECRET`, `SOCIAL_X_ACCESS_TOKEN`, `SOCIAL_X_ACCESS_SECRET`, `SOCIAL_X_BEARER_TOKEN`, `SOCIAL_LI_ACCESS_TOKEN`, `SOCIAL_TG_BOT_TOKEN`, `SOCIAL_WEBHOOK_URL`, `SOCIAL_WEBHOOK_SECRET`; the webhook address is treated like a password: Zapier / Make / IFTTT addresses are credentials). A stored key that cannot be read (changed `APP_KEY`) stops its channel instead of sending unsigned. "Post again" cannot double-post (a version check, a lock and a 2-minute pause), only a rejected token's failed posts are re-queued after you paste a new one (last 48 hours, issues still public), and a role with only "Share newsletters" cannot open unpublished issues. **Nothing was ever tried against a real platform**: use **Test connection** and **Send a test post** on each channel first. Sixth optional cron job, every 5 minutes, retries posts that did not go through (with growing pauses, five tries at most; an unclear time-out is left for you to check, never posted twice by itself): `0-59/5 * * * *  /usr/bin/php /home/ACCOUNT/domains/DOMAIN/public_html/bin/social-dispatch.php > /dev/null 2>&1`. ## Layout

```
index.php   front controller          app/        code (core, controllers, models, views, config, routes)
assets/     css js img (static)       uploads/    user-uploaded images
storage/    private runtime data      database/   schema.sql, seed.sql
scss/       styles (compiled to assets/css)       bin/  setup, create-admin, build-scss, selftest
docs/       ARCHITECTURE.md, DESIGN.md, CONTENT_NOTES.md, live-snapshot/
```

## Documentation

* `docs/DESIGN.md` - the public design system: tokens, contrast table, component markup, JS hooks, per-section recipes. Read it before touching `scss/` or the public views.
* `docs/ARCHITECTURE.md` - developer contract: structure, APIs, CMS page registry, URL map, security rules.
* `docs/MEMBERSHIP.md` - the membership feature: data model, fee configuration, status workflow, service API, routes, privacy rules and the owner to-do list.
* `docs/MEMBERSHIP_CARD.md` - the membership card: headshot and proof-of-payment uploads, the private "My membership" page, the verification (QR) page, the card engine (pure-PHP PDF writer and QR encoder), the card designer (every word on the card is editable), issue triggers, the review fixes (section 15: strict PDF scan, retention of the card photo, analytics off on credential pages, rate limits) and the live-database upgrade notes.
* `docs/NEWSLETTER.md` - the newsletter: JSON content model, issue workflow, admin editor and JSON API, public pages, e-mailing queue, SMTP driver, mock SMTP server, privacy notes.
* `docs/PARTNERS_NEWSLETTER.md` - partners section, logo pipeline, PDF newsletters, live-reflection (cache) audit, schema/seed upgrade rules and known limits.
* `docs/CALENDAR.md` - the calendar: data model, repeat rules, date engine, public and admin routes, JSON and iCal shapes, the sources of every seeded date and what could not be verified.
* `docs/SHOP.md` - the shop: data model, money rules, order and payment state machines, the Flutterwave flow and its secrets, routes, abilities, sample content and the owner to-do list.
* `docs/CONTENT_NOTES.md` - where the starter wording comes from and what the owner still has to confirm or supply.
* `docs/live-snapshot/` - text of the live site pages used as the content source.
